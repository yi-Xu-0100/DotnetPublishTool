# 设计说明

## 目标与硬约束

按用户需求，工具有一条硬约束：**不修改源项目里的任何文件**。因此「改发布配置」不能去改 `Properties/PublishProfiles/*.pubxml`，而必须把改动落到输出目录的副本上，再让这次发布使用副本。

唯一的例外是 MSI 面板里显式勾选的「并把新版本写回项目 csproj」（默认关闭）：它按用户要求把自动递增后的版本写进项目 `<Version>`，写前先把原文件备份到输出目录。

## 分层

- `DotnetPublishTool.Core`：全部发布逻辑，纯 `net10.0`，不引用 WPF，可被冒烟工具直接调用。
- `DotnetPublishTool.App`：WPF 界面，手写 MVVM（`ObservableObject` / `RelayCommand` / `AsyncRelayCommand`），不引入第三方包。
- `DotnetPublishTool.Smoke`：无界面端到端验证。

编排集中在 `PublishWorkflow`：合并属性 → 写配置副本 → 清理发布目录 → 构造命令 → 执行 → 打包。

## 关键机制：从项目外部加载发布配置

实测确认（本机 .NET SDK 10.0.401）：

- `dotnet publish <proj> -p:PublishProfile=<名>` 只会在项目内查找 `Properties/PublishProfiles/<名>.pubxml`。
- 改为传 **`-p:PublishProfileFullPath=<绝对路径>`**，MSBuild 会直接 import 这个路径上的 `.pubxml`，无论它在哪。证据：`dotnet msbuild <proj> -p:PublishProfileFullPath=<外部路径> -getProperty:WebPublishProfileFile -getProperty:PublishProfileImported` 返回该外部路径且 `PublishProfileImported=true`。

因此流程是：`<输出目录>/<项目名>/profiles/<配置名>.pubxml` → 用 `PublishProfileFullPath` 发布。源目录保持只读。

另一个实测结论：`-o <目录>` 作为全局属性会覆盖配置里的 `PublishDir`，所以输出位置由工具统一控制。

## 属性如何合并

发布配置本质就是一组 MSBuild 属性。工具把它们分成两类：

- **常用项**（`PublishOptionKeys.Curated`）：绑定「常用设置」面板，发布时由界面值覆盖。
- **其他项**：原样进「其他属性」表格，读写往返，不被丢弃（例如 `Platform`、`PublishProtocol`、`_TargetId`、`DeleteExistingFiles`）。

`BuildEffectiveProperties` 负责合并；`PublishProtocol` / `_TargetId` 只在源配置缺失时补默认值，不覆盖用户已有的值。写出时按 `PreferredOrder` 排序，让 `.pubxml` 稳定易读。

四个布尔开关（自包含 / 单文件 / ReadyToRun / 裁剪）**总是显式写出并显式传给命令行**，避免界面显示与实际产物不一致。

## 不改源文件的保证

- 读配置：只读。
- 写配置：只写 `<输出根>/<项目名>/profiles/`。
- 发布：`dotnet publish` 会把中间产物写进源项目的 `bin/obj`——这是构建产物，不属于源文件；除此之外不动源目录。
- 已验证：发布前后源 `.pubxml` 的哈希与修改时间不变。

## 输出路径一律绝对化

`dotnet publish` 的工作目录被设为项目目录，命令行里的相对 `-o` / `PublishProfileFullPath` 会被解析到项目目录下。因此 `PublishWorkflow` 用 `Path.GetFullPath` 把输出根目录规整为绝对路径后再使用。这个坑在开发中真实出现过：相对输出根目录导致产物落到项目目录下、发布目录为空、zip 为空包。

## 压缩包

`ZipPackager` 手工遍历发布目录并指定条目名，而不是用 `ZipFile.CreateFromDirectory` 的 `includeBaseDirectory`——后者的顶层文件夹名取自源目录（会变成 `publish`）。顶层文件夹名固定用项目名。

命名由 `ZipNaming.Resolve` 解析；默认口径为「项目名_日期」，格式 `yyyyMMdd_HHmmss`（精确到秒，避免同日互覆）。
版本号会去掉语义化版本的 `+buildmetadata`，并对整名做文件名字符净化（`:` 等非法字符会替换掉）。

## MSI 安装包

`MsiPackageBuilder` 把发布目录做成「装到 Program Files」的 MSI。不依赖 WiX、不联网，只用系统自带的 `msi.dll` 与 `makecab.exe`。

- **数据库**：`MsiDatabase` 通过 P/Invoke（`MsiNative`）直接调 msi.dll：建表 → 插行 → 插流 → 写摘要信息 → `MsiDatabaseCommit`。踩过的坑：**`MsiCreateRecord` 与其它 API 不同，它直接返回记录句柄（失败为 0）**，不是「错误码 + out 参数」。
- **表结构**：Property / Directory / Feature / Component / File / FeatureComponents / Media / Upgrade / Shortcut / InstallExecuteSequence / InstallUISequence。每个文件一个组件，组件 GUID 由「升级代码 + 相对路径」稳定推导（`StableGuid`）；组件按 PE 头判断位数并写 64 位属性。
- **cab**：`CabinetBuilder` 生成 DDF 再调 `makecab.exe`。DDF 里只出现 ASCII 条目名，makecab 的工作目录就是暂存目录 —— 这样中文/空格路径不会在 makecab 的 ANSI 解析里出错；文件先复制到暂存目录并按 `f0001_<名字>` 重命名，这个名字同时是 cab 条目名和 File 表的 `File` 列。cab 以 `#app.cab` 内嵌进 `_Streams`，安装包因此只有一个文件。
- **摘要信息**（最容易漏、漏了引擎直接返回 87「参数错误」的地方）：
  - `Codepage`（PID 1，VT_I2）**必须在写第一个字符串之前**设置 —— 摘要信息里的字符串是按它转 ANSI 存的；
  - `Revision Number`（PID 9）必须是**带花括号的 GUID**（`{XXXXXXXX-XXXX-...}`），也就是包码；写成 32 位纯十六进制会被引擎拒收；
  - `Page Count`（PID 14）= 要求的最低安装器版本（64 位包要求 ≥ 200，这里写 200）；
  - `Word Count`（PID 15）是位域：bit1(2)=源是压缩的，bit3(8)=安装不需要提升权限；**每机器安装**（装到 Program Files）不能加 bit3，所以写 2；
  - `Security`（PID 19）= 2（安装数据库建议标成「推荐只读」）。
  - 这四个值 + Codepage 的**设置顺序**踩过一次坑：全都对不上时，`msiexec /i` 与 `/a` 都在「打开安装包」阶段直接返回 87，日志里一条动作都没有。
- **序列**：`InstallUISequence` 只有 FindRelatedProducts/CostInitialize/FileCost/CostFinalize/**ExecuteAction** —— 少了 ExecuteAction，双击安装会什么都不做。`InstallExecuteSequence` 用标准顺序，`RemoveExistingProducts` 排在 `InstallInitialize` 之后（先装新、再卸旧的大版本升级）。
- **管理安装**：`/a` 走的是 `AdminExecuteSequence`/`AdminUISequence`，其中真正铺文件的是 **`InstallAdminPackage`**。没有这两张表时 `/a` 会「成功但什么都不解出来」——踩过一次。
- **命名与版本**：文件名复用 zip 的四口径（`ZipNaming.Resolve` 加了扩展名参数），默认「产品名_版本号」；`MsiVersion.Normalize` 把任意版本规整成 `x.y.z`（前两段 ≤255、第三段 ≤65535）。
- **位数**：`PeArchitecture` 读启动 exe 的 PE 头决定 64/32 位：64 位用 `ProgramFiles64Folder`、组件属性 256、`Template=x64;1033`；识别不出来时按当前操作系统。
- **失败不回滚发布**：安装包生成失败只写进 `PublishResult.MsiError` 并弹一次提示，发布产物照旧可用。
- **升级**：升级代码由「发布者 + 产品名」稳定推导（可用 `MsiOptions.UpgradeCode` 固定），产品码由「升级代码 + 版本」推导 —— 同版本重装是修复，换版本是大版本升级。
- 排障开关：环境变量 `DOTNETPUBLISHTOOL_KEEP_MSI_STAGING=1` 时保留暂存目录（含 cab 与 package.msi）。
- **版本自动递增**（`MsiVersionService`，默认关闭）：
  - 在 `SaveProfile` 里、写配置副本**之前**解析，所以产物、zip 名、安装包与写回项目用的是同一个版本号；
  - 项目版本由 `ProjectInspector.PickBestVersion` 从**项目文件里显式声明**的版本键里挑数值最大的那个（`Version`/`VersionPrefix`、`InformationalVersion`、`FileVersion`、`AssemblyVersion`，并列时优先 `Version`）：SDK 由 `<Version>` 推导出来的值不算独立来源，否则手动改小会被推导值顶住（看起来就是「版本降不回来」）；项目文件里看不到版本时退回 MSBuild 评估值；
  - 基准优先级「MSI 显式版本 → 版本覆盖 → 项目版本」；**写回模式下项目文件是唯一真相**（手动改小/改回去立刻生效），只有不写回时才与本机记录取较大者（否则会反复产出同号安装包）；
  - 递增保留原有段数（1.4 → 1.5、1.4.2 → 1.4.3、2.1.2.0 → 2.1.3.0，尾段清零），且**一定落在前三段**（否则 MSI 版本不变、升级失效）；按上限进位（第三段 >65534 → 第二段 +1，第二段 >255 → 第一段 +1；65534 是 AssemblyVersion 与 MSI 里更严的那个），大段到 255 或解析不出版本时抛 `PublishException`（宁可失败也不产错包）；
  - 写回用 `CsprojVersionEditor`：**只替换「值等于基准版本」的那些版本键**（四个键都认；被刻意钉住的 `AssemblyVersion` 不会被误改），一个都不匹配时才改/插 `<Version>`；全程只做元素文本替换（不做 XML 往返，否则会丢 XML 声明后的换行、把声明改成 utf-16、影响注释与缩进），没有 `PropertyGroup` 或文件不是 UTF-8 就直接报错；
  - 写回前把原 csproj 备份到 `<输出根>/<项目名>/csproj-backup/`（保留最近 5 份）；不写回时版本记在 `%APPDATA%\DotnetPublishTool\msi-versions.json`（不可写退到 `%TEMP%`）；
  - 只有安装包真的生成成功才推进版本 —— MSI 失败时版本不变，重跑同一个号。

## 最近项目记录

- 记录存放在 `AppSettings.RecentProjects`，元素是 `RecentProject`（`FilePath` + `LastUsed`）。
- 载入项目 / 解决方案成功后调用 `MainViewModel.RecordRecent`：按路径去重（忽略大小写）、插到最前、截断到 20 条，并立即持久化。
- `DisplayName` 由路径现算（`[JsonIgnore]`，不落盘），取「文件名 —— 末尾两级目录」；同名项目靠这两级目录区分，完整路径放在悬停提示里。
- 直接写 `_selectedRecentProject` 字段而不是走属性 setter，避免"记录 → 选中 → 再次载入"的递归。
- 启动时 `OnWindowLoaded` 取最近一个仍然存在的记录恢复；选中的记录若已被删除，提示并从列表移除。

## 设置文件的存放

默认 `%APPDATA%\DotnetPublishTool\settings.json`。该位置不可写时（受限账户、沙箱/低完整性进程）`AppSettingsService`
按「已生效路径 → 主路径 → `%TEMP%\DotnetPublishTool\settings.json`」依次尝试读写，成功后固定下来。

## 输出目录的可用性

默认输出根目录在「文档」下，但有些环境会拒绝写入：受控文件夹访问（Defender）、受限账户、沙箱/低完整性进程等。

- `OutputDirectoryService.TryEnsureWritable` 会 `CreateDirectory` 后再**真实写一个探测文件**，而不是只看目录是否存在。
- 失败时 `MainViewModel.EnsureOutputRootUsable` 依次尝试 `%LOCALAPPDATA%`、`%USERPROFILE%`、`%TEMP%` 下的 `DotnetPublishTool`，
  改用第一个可写目录，并弹窗 + 日志告知；一个都没有才报错。
- 这一步在 `BuildRequest` **之前**执行，否则请求里带的是旧的输出根目录。
- 项目目录同样会被探测：`dotnet publish` 要写 `obj/bin`，不可写时提前警示，避免只看到 MSBuild 的报错。
- 底层失败被包装成 `PublishException`（消息直接面向用户），冒烟工具据此打印可读原因而不是未处理异常。

## 界面

- 左：发布配置列表；右：常用设置 / 其他属性 / 配置预览三个页签。
- 项目信息与版本通过 `dotnet msbuild -getProperty:...` 评估获得，比静态解析 csproj 准确；评估失败时退回静态解析并在日志里提示。
- 项目类型（WPF / WinForms / Web / 控制台 / 类库 / 测试）用于提示与默认配置。
- 设置存 `%APPDATA%/DotnetPublishTool/settings.json`。

## 进程完整性自检

`ProcessIntegrity` 用 P/Invoke `GetTokenInformation(TokenIntegrityLevel)` 读当前进程的完整性级别。
**实现注意**：`WindowsIdentity.GetCurrent().Groups` **不包含**完整性 SID（实测），只能查令牌。

动机与通用规则见全局 `~/.dsh/AGENTS.md`（完整性级别一节），这里只记本仓库的落点：
启动时把级别写进日志；输出目录不可写且级别低于 Medium 时，弹窗与日志直接给出原因与
`tools/fix-build-integrity.ps1`。

## 日志回调必须串行

`DotnetProcessRunner` 分别在两个线程上读 stdout 与 stderr，而 `Progress<T>` 在同步上下文为空时会**就地**调用回调（无界面自检与冒烟工具就是这种情况）。若两个线程同时回调同一个 `StringBuilder` / `List`，会偶发 `0xE0434352` 进程崩溃（开发中真实出现过，表现为「产物已写出但结果文件缺失」）。因此运行器用锁把日志回调串行化，界面与冒烟工具的日志缓冲各自再加一层锁。

## 验证

- `--selftest`：构造真实窗口（验证 XAML 与资源能加载），再驱动 ViewModel 完成一次真实发布 + 打包（`--zip` / `--msi`），把结果写成 JSON。无界面自检时先把 `SynchronizationContext` 置空，避免阻塞 UI 线程与 Dispatcher 互相等待。
- `DotnetPublishTool.Smoke`：不依赖 WPF 的端到端验证，覆盖配置发现、配置副本写出、发布、三种 zip 命名，以及 `pack-msi`（把已发布目录做成 MSI）。
- MSI 结构验证（沙箱内 msiexec 连不上安装服务）：用 WindowsInstaller COM 打开 msi 读各表，从 `_Streams` 取出 cab、`expand` 解开后与发布目录逐文件比对 SHA256。这只能证明「文件打包对」，证明不了「引擎收不收」。
- MSI 行为验证（**必须在沙箱之外、需要授权**）：
  - `msiexec /a <msi> /qn TARGETDIR=<目录>` 验证管理安装与整条 Admin 序列；
  - 真实安装用**每用户安装 + 覆盖安装目录**，不写 Program Files、可随时卸载：
    `msiexec /i <msi> /qn ALLUSERS=2 MSIINSTALLPERUSER=1 INSTALLFOLDER=<目录>`，随后 `msiexec /x <msi> /qn`；
  - 排障时用 `/l*v`（或 `/l*vx`）看日志：**引擎在「打开安装包」阶段失败时，日志里一条 `Action start` 都不会有**。

## 已知限制

- 只支持 SDK 风格项目。
- 只做 FileSystem 文件夹发布。
- 需要额外 NuGet 包的选项（单文件、自包含、裁剪相关）在离线环境下会 `NU1301`，错误原样透出。
- MSI 安装包不写 Dialog/Control 表，因此**没有安装向导**；只做每机器安装（`ALLUSERS=1`），装到 Program Files 需要管理员权限；不做代码签名。
