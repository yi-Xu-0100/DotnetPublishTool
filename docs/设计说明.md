# 设计说明

## 目标与硬约束

按用户需求，工具有一条硬约束：**不修改源项目里的任何文件**。因此「改发布配置」不能去改 `Properties/PublishProfiles/*.pubxml`，而必须把改动落到输出目录的副本上，再让这次发布使用副本。

## 分层

- `DotnetPublishTool.Core`：全部发布逻辑，纯 `net10.0`，不引用 WPF，可被冒烟工具直接调用。
- `DotnetPublishTool.App`：WPF 界面，手写 MVVM（`ObservableObject` / `RelayCommand` / `AsyncRelayCommand`），不引入第三方包。
- `DotnetPublishTool.Smoke`：无界面端到端验证。

编排集中在 `PublishWorkflow`：合并属性 → 写配置副本 → 清理发布目录 → 构造命令 → 执行 → 打包。

## 关键机制：从项目外部加载发布配置

实测确认（本机 .NET SDK 10.0.401）：

- `dotnet publish <proj> -p:PublishProfile=<名>` 只会在项目内查找 `Properties/PublishProfiles/<名>.pubxml`。
- 改为传 **`-p:PublishProfileFullPath=<绝对路径>`**，MSBuild 会直接 import 这个路径上的 `.pubxml`，无论它在哪。证据：`dotnet msbuild <proj> -p:PublishProfileFullPath=<外部路径> -getProperty:WebPublishProfileFile -getProperty:PublishProfileImported` 返回该外部路径且 `PublishProfileImported=true`。

因此流程是：`<输出目录>/<项目名>/profiles/<配置名>.pubxml` → 用 `PublishProfileFullPath` 发布。源目录保持只读。

另一个实测结论：`-o <目录>` 作为全局属性会覆盖配置里的 `PublishDir`，所以输出位置由工具统一控制。

## 属性如何合并

发布配置本质就是一组 MSBuild 属性。工具把它们分成两类：

- **常用项**（`PublishOptionKeys.Curated`）：绑定「常用设置」面板，发布时由界面值覆盖。
- **其他项**：原样进「其他属性」表格，读写往返，不被丢弃（例如 `Platform`、`PublishProtocol`、`_TargetId`、`DeleteExistingFiles`）。

`BuildEffectiveProperties` 负责合并；`PublishProtocol` / `_TargetId` 只在源配置缺失时补默认值，不覆盖用户已有的值。写出时按 `PreferredOrder` 排序，让 `.pubxml` 稳定易读。

四个布尔开关（自包含 / 单文件 / ReadyToRun / 裁剪）**总是显式写出并显式传给命令行**，避免界面显示与实际产物不一致。

## 不改源文件的保证

- 读配置：只读。
- 写配置：只写 `<输出根>/<项目名>/profiles/`。
- 发布：`dotnet publish` 会把中间产物写进源项目的 `bin/obj`——这是构建产物，不属于源文件；除此之外不动源目录。
- 已验证：发布前后源 `.pubxml` 的哈希与修改时间不变。

## 输出路径一律绝对化

`dotnet publish` 的工作目录被设为项目目录，命令行里的相对 `-o` / `PublishProfileFullPath` 会被解析到项目目录下。因此 `PublishWorkflow` 用 `Path.GetFullPath` 把输出根目录规整为绝对路径后再使用。这个坑在开发中真实出现过：相对输出根目录导致产物落到项目目录下、发布目录为空、zip 为空包。

## 压缩包

`ZipPackager` 手工遍历发布目录并指定条目名，而不是用 `ZipFile.CreateFromDirectory` 的 `includeBaseDirectory`——后者的顶层文件夹名取自源目录（会变成 `publish`）。顶层文件夹名固定用项目名。

命名由 `ZipNaming.Resolve` 解析；默认口径为「项目名_日期」，格式 `yyyyMMdd_HHmmss`（精确到秒，避免同日互覆）。
版本号会去掉语义化版本的 `+buildmetadata`，并对整名做文件名字符净化（`:` 等非法字符会替换掉）。

## 最近项目记录

- 记录存放在 `AppSettings.RecentProjects`，元素是 `RecentProject`（`FilePath` + `LastUsed`）。
- 载入项目 / 解决方案成功后调用 `MainViewModel.RecordRecent`：按路径去重（忽略大小写）、插到最前、截断到 20 条，并立即持久化。
- `DisplayName` 由路径现算（`[JsonIgnore]`，不落盘），取「文件名 —— 末尾两级目录」；同名项目靠这两级目录区分，完整路径放在悬停提示里。
- 直接写 `_selectedRecentProject` 字段而不是走属性 setter，避免"记录 → 选中 → 再次载入"的递归。
- 启动时 `OnWindowLoaded` 取最近一个仍然存在的记录恢复；选中的记录若已被删除，提示并从列表移除。

## 设置文件的存放

默认 `%APPDATA%\DotnetPublishTool\settings.json`。该位置不可写时（受限账户、沙箱/低完整性进程）`AppSettingsService`
按「已生效路径 → 主路径 → `%TEMP%\DotnetPublishTool\settings.json`」依次尝试读写，成功后固定下来。

## 输出目录的可用性

默认输出根目录在「文档」下，但有些环境会拒绝写入：受控文件夹访问（Defender）、受限账户、沙箱/低完整性进程等。

- `OutputDirectoryService.TryEnsureWritable` 会 `CreateDirectory` 后再**真实写一个探测文件**，而不是只看目录是否存在。
- 失败时 `MainViewModel.EnsureOutputRootUsable` 依次尝试 `%LOCALAPPDATA%`、`%USERPROFILE%`、`%TEMP%` 下的 `DotnetPublishTool`，
  改用第一个可写目录，并弹窗 + 日志告知；一个都没有才报错。
- 这一步在 `BuildRequest` **之前**执行，否则请求里带的是旧的输出根目录。
- 项目目录同样会被探测：`dotnet publish` 要写 `obj/bin`，不可写时提前警示，避免只看到 MSBuild 的报错。
- 底层失败被包装成 `PublishException`（消息直接面向用户），冒烟工具据此打印可读原因而不是未处理异常。

## 界面

- 左：发布配置列表；右：常用设置 / 其他属性 / 配置预览三个页签。
- 项目信息与版本通过 `dotnet msbuild -getProperty:...` 评估获得，比静态解析 csproj 准确；评估失败时退回静态解析并在日志里提示。
- 项目类型（WPF / WinForms / Web / 控制台 / 类库 / 测试）用于提示与默认配置。
- 设置存 `%APPDATA%/DotnetPublishTool/settings.json`。

## 进程完整性自检

`ProcessIntegrity` 用 P/Invoke `GetTokenInformation(TokenIntegrityLevel)` 读当前进程的完整性级别。
**实现注意**：`WindowsIdentity.GetCurrent().Groups` **不包含**完整性 SID（实测），只能查令牌。

动机与通用规则见全局 `~/.dsh/AGENTS.md`（完整性级别一节），这里只记本仓库的落点：
启动时把级别写进日志；输出目录不可写且级别低于 Medium 时，弹窗与日志直接给出原因与
`tools/fix-build-integrity.ps1`。

## 日志回调必须串行

`DotnetProcessRunner` 分别在两个线程上读 stdout 与 stderr，而 `Progress<T>` 在同步上下文为空时会**就地**调用回调（无界面自检与冒烟工具就是这种情况）。若两个线程同时回调同一个 `StringBuilder` / `List`，会偶发 `0xE0434352` 进程崩溃（开发中真实出现过，表现为「产物已写出但结果文件缺失」）。因此运行器用锁把日志回调串行化，界面与冒烟工具的日志缓冲各自再加一层锁。

## 验证

- `--selftest`：构造真实窗口（验证 XAML 与资源能加载），再驱动 ViewModel 完成一次真实发布 + 打包，把结果写成 JSON。无界面自检时先把 `SynchronizationContext` 置空，避免阻塞 UI 线程与 Dispatcher 互相等待。
- `DotnetPublishTool.Smoke`：不依赖 WPF 的端到端验证，覆盖配置发现、配置副本写出、发布、三种 zip 命名。

## 已知限制

- 只支持 SDK 风格项目。
- 只做 FileSystem 文件夹发布。
- 需要额外 NuGet 包的选项（单文件、自包含、裁剪相关）在离线环境下会 `NU1301`，错误原样透出。
